一、架构选型决策阶梯：别把简单问题复杂化

🧭 四级复杂度递进选型指南（源自 Anthropic & OpenAI 工程实践共识）
Level 0 → 确定性业务代码
无需调用 LLM
输入输出规则完全固定（如按输入单号查库、固定公式算税费）。最快、零幻觉、零 Token 成本。
Level 1 → 单次结构化 LLM 调用
1 次 API 推理
摘要、翻译、分类、从工单文本提取 JSON 字段，所有输入材料在调用前已一次性备齐。
Level 2 → 编排工作流 (Workflow)
代码掌控步骤顺序
多步流程可预先穷举（如：意图分类路由 → 固定检索制度 → 生成合规回复），可预测性极高。
Level 3 → 自主智能体 (ReAct Agent)
模型动态决定下一步
下一步查什么取决于上一步查到了什么（如故障根因排查、复杂多条件售后诊断），须配双重预算熔断与 Eval。

三、MCP 协议速查：JSON-RPC 2.0 信封格式与三大原语对照

📨 JSON-RPC 2.0 三种核心报文信封
  • Request（请求包，必含非空 id）：
    {"jsonrpc":"2.0", "id":1, "method":"tools/call", "params":{...}}
  • Response（响应包，原样回传 id）：
    成功返回 "result":{...}；失败返回 "error":{"code":-32601,"message":"..."}
  • Notification（单向通知，无 id 字段）：
    {"jsonrpc":"2.0", "method":"notifications/initialized"}（发完即走不回信）
⚠️ Stdio vs Streamable HTTP 实战要点
  • Stdio 本地子进程传输：按换行符分隔一行一个 JSON-RPC 包走 stdin/stdout；严禁在服务端使用普通 print()，日志必须打往 sys.stderr。
  • Streamable HTTP 远程传输：客户端通过 HTTP POST 发送 JSON-RPC，支持按请求开启 SSE 事件流推送进度，配合 OAuth 2.1 / Bearer 鉴权。
MCP 原语 控制主体 Python FastMCP 实现装饰器 JSON-RPC 方法对 实现后在客户端 / 应用里的真实效果
Tools（工具） 大模型提议
(Model-controlled)		 @mcp.tool() tools/list
tools/call		 转换为 LLM tools 参数；模型遇到查实时订单、提工单需求时自动申请触发。
Resources（资源） 应用 / 用户挂载
(Application-controlled)		 @mcp.resource("policy://{id}") resources/list
resources/read		 类似聊天框里的 @文件 引用菜单，用户或程序直接按 URI 无副作用读入制度、配置与表结构。
Prompts（模板） 用户主动选用
(User-controlled)		 @mcp.prompt() prompts/list
prompts/get		 在输入框敲 / 弹出快捷指令表单（如 /audit_refund A100），一键填充专家级审查提示词。
