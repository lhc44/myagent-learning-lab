# 第 7 章：管理对话长度（上下文）与按意思查文档（RAG）

> **第三阶段 · 连接与扩展** · 30 分钟 · 配套 lab07_context_rag.py

聊天记录越来越长、公司制度文档好几百页，全塞进一次请求里既费钱又容易让模型抓不住重点。本章只解决两个特别接地气的工程问题：1）删旧聊天记录时怎么删才不会触发接口报错？2）用户问『退钱』而文档标题叫『退款规定』，怎么按意思把相关段落搜出来喂给模型？

## 本章学习目标
- 学会清理超长聊天记录的唯一铁律：永远留住开头的 System 指令，且『模型调工具 + 工具回结果』必须成对留或成对删
- 分清三种数据该放哪：当前聊天列表（Context）、用户长期习惯（Memory）、实时订单数据库（业务库）
- 搞懂 RAG（检索增强生成）的工程流程：调接口把文字变向量 → 数据库按相似度查前几条 → 塞进提示词让模型照着答

> [!TIP]
> **🧭 工程师减负指南：本章什么必会？什么不用死磕？**
> - **✅ 工程实战必会**：1）清理旧消息时绝对不能留下『没有前文调用申请的孤立 tool 消息』；2）做知识库问答（RAG）的四个工程步骤：切分段 → 调 /embeddings 接口转数字列表 → 按相似度取前几名（越接近 1 越相关）→ 连同问题发给模型。
> - **🪶 放心做减法**：⚠️ 零数学要求！你完全不需要记『余弦相似度』的数学公式，也不需要研究向量空间几何！真实项目里 PostgreSQL (pgvector)、Milvus 或框架的一句 similarity_search() 就直接帮你把排好序的文档查出来了。实验代码里那 4 行乘除法仅仅是为了让你本地不用装数据库也能跑出分数看效果。

## 从传统 / 单次 LLM API 视角过渡
- **过去熟悉的做法**：初学者的粗暴做法：messages.append(...) 无限往列表里塞，超长了就简单 messages = messages[-10:] 切片——结果经常把模型的调用申请切掉了、只剩半截工具返回，当场触发 HTTP 400 崩溃！
- **AI Agent 工程视角**：稳妥的工程做法：删旧历史时把『模型提调用 + 工具回结果』绑成一组同生共死；查公司文档时用向量检索把最相关的两三段挑出来再发给模型。

> [!WARNING]
> **🎭 真实翻车现场：每聊到第 6 轮就准时报 HTTP 400 的诡异 Bug**
> 某团队上线后发现用户前 5 句聊天丝滑无比，一到第 6 句就大概率报错退出。排查半天才发现，后台写了 history = [history[0]] + history[-8:] 做定长截断——当倒数第 8 条刚好切在『工具返回结果（role: tool）』上时，它前面的 assistant(tool_calls) 被切丢了，OpenAI 接口当场判定消息序列非法返回 400！改用本章的『原子单元成组裁剪』后故障彻底清零。

## 核心数据流：Agentic RAG + 上下文组装的四步标准流水线
| 步骤流向 | 关键动作 | 详细说明 |
| :--- | :--- | :--- |
| `1. 语义向量化` → `Embedding 模型` | **问题转高维浮点向量** | 『付了钱没发货怎么把钱退回来』 → [0.94, 0.28, ...] |
| `2. 相似度召回` → `知识库分块 (Chunks)` | **余弦相似度 Top-K + 权限过滤** | 精准命中 P1《退款管理制度》(score=0.996)，过滤无关物流与上线制度 |
| `3. 配对安全裁剪` → `trim_history_safely()` | **守护 Token 预算与协议完整性** | 置顶 System 指令，整组淘汰过早的旧对话与旧工具调用对 |
| `4. 基于证据生成` → `LLM 推理与引用` | **有据可查，无据拒答** | 结合实时订单状态 + 召回的 P1 原文生成带出处的可靠答复 |

## 7.1 上下文窗口不是垃圾桶：Token 预算与『中间迷失效应』

斯坦福大学等机构的经典研究《Lost in the Middle: How Language Models Use Long Contexts》（Liu et al.）揭示了一个重要现象：当输入上下文塞满大量无关噪声文档时，大模型对位于上下文中部关键事实的提取准确率会显著下降，同时首字延迟（TTFT）与费用随输入 Token 数呈线性甚至超线性增长。因此工业界越来越推崇用 **Context Engineering（上下文工程）** 替代狭义的 Prompt Engineering——核心目标是在每一轮推理时，只把**高信噪比、恰到好处的信息**放进模型的注意力窗口。

做预算规划时，遵循公式：**可用历史与资料预算 = 模型上下文上限 - 预留最大输出 Token - System 指令与工具 Schema 开销 - 安全估算余量**。更关键的是裁剪历史时的协议铁律：`assistant`（含 `tool_calls`）与紧随其后的所有 `role: 'tool'` 消息必须视为一个不可分割的**原子单元（Atomic Unit）**，要么一起保留，要么一起淘汰或替换为一段纯文本摘要，绝不能只留一半！

## 7.2 别把三种『记忆』混为一谈

很多教程笼统地谈“给 Agent 加记忆”，结果开发者把订单发货状态也存进向量记忆库里，酿成大祸。请严格区分三类状态存储：

• **工作上下文（Working Context）**：当前这次任务正在使用的 messages 列表与中间工具观察结果，任务结束即可归档。

• **长期用户/经验记忆（Long-Term Memory）**：跨会话有价值的个性化偏好或经核实的经验（例如『该财务总监偏好以 Markdown 表格查看月度汇总』），需标注来源、时间戳与有效期，支持用户查看与删除。

• **权威业务系统（System of Record）**：订单是否付款、库存还剩多少、审批是否通过——这些实时交易事实**永远只能以关系型数据库或核心业务微服务的实时查询为准**，绝不能靠翻查上礼拜的聊天记忆摘要来回答！

## 7.3 用户说『退钱』而文档写『退款』：怎样按意思搜出相关制度（RAG）？

当公司有几百份规章制度时，既塞不进单次请求，又不能只靠 SQL 的 `LIKE '%退款%'` 死板匹配关键字——因为用户的口语五花八门，他可能问『已经付钱了但还没寄出来，怎么把钱要回来？』，整句话里根本没有出现『退款』两个字！

工程上解决这个问题的标准套路叫 **RAG（检索增强生成，说白了就是：先搜出相关段落，再让模型照着答）**。怎么做到『按意思搜索』呢？靠的是大模型厂商提供的另一个现成接口——**文本向量化（`/v1/embeddings`）**：你传一句话进去，接口返回一串小数（例如 `[0.94, 0.28, ...]`）。神奇之处在于，不管字面用词怎么变，只要两句话表达的意思相近，接口算出来的这两串数字就非常接近！

在后端代码里，你只需要对比用户问题与每段文档的**相似度得分（范围在 -1 到 1 之间，越接近 `1.0` 代表意思越像，接近 `0` 代表毫不相干）**，挑出得分最高的 1~3 段制度塞进提示词交给大模型作答即可。在真实生产项目中，连这步打分排序都由向量数据库（如 PostgreSQL 的 `pgvector` 插件）一句 SQL 自动算好，**做工程开发完全不需要手推任何数学公式**！如果最高得分依然很低，说明制度库里压根没相关规定，直接让模型诚实回答『未查到相关条款』。

## 🔬 专业术语与底层方法显微镜（四步拆解）

### 1. [🔥 工程实战核心] 文档分块（Chunking + Overlap 重叠窗口）是怎么切、为什么切？
- **① 大白话本质**：一本 50 页的《员工手册》不能整本算一个向量（语义太杂糊成一团），也不能按固定 200 个字一刀切（刚好把『满 200 元 | 须经人工审批』从中间劈成两半，两边意思全残废了）！正确做法是按段落/标题切块，并在相邻两块之间留出 10%~15% 的**重叠复读区（Overlap）**。
- **② 底层协议与工作机制**：假设每块目标长度 300 字、重叠窗口 50 字：第 1 块取第 0~300 字，第 2 块不是从 301 字开始，而是退回来从第 250~550 字开始！这样即使一句关键规则恰好压在 300 字边界上，它在第 2 块开头依然是完整不断裂的一整句话。同时每个 Chunk 都要附带元数据（文档标题、章节号、生效日期、允许访问的部门列表）。
- **③ 标准实现代码（Python · 10 行写一个带重叠窗口（Overlap）的滑动分块函数）**：
```python
def chunk_text_with_overlap(text: str, chunk_size: int = 200, overlap: int = 40) -> list[str]:
    step = chunk_size - overlap
    chunks = []
    for start in range(0, len(text), step):
        piece = text[start : start + chunk_size]
        if piece:
            chunks.append(piece)
        if start + chunk_size >= len(text):
            break
    return chunks
```
- **④ 实现后的真实效果**：实现后效果：既保证了每个向量片段主题集中、检索相似度区分度高，又彻底消除了『关键条件刚好卡在切分缝隙里导致模型看漏半句话』的经典 RAG 事故。

### 2. [🪶 选读拓展] Embedding 向量与相似度分数的直观理解（无需任何数学公式）
- **① 大白话本质**：【选读背景 · 不用背公式】别被『1536 维向量空间』和『余弦相似度』这种数学词吓退！做工程开发你只需要把它想象成『给每句话打一组特征标签分』。
- **② 底层协议与工作机制**：• 比如句子 A『怎么退钱』经过 `/embeddings` 接口变成 `[0.95, 0.20]`；
• 制度 P1『退款管理规定』变成 `[0.92, 0.22]` —— 两组数字长得很像，数据库算出来的相似度得分是 `0.99`（满分 1.0），说明意思几乎一样！
• 制度 P3『服务器上线规范』变成 `[0.02, 0.01]` —— 数字差很远，得分接近 `0`，说明毫不相干。
在真实公司项目里，存数字和算分排序全由向量数据库（如 PostgreSQL `pgvector`）一句查询自动完成，你连加减乘除都不用自己写！
- **③ 标准实现代码（Python · 从文本到 Top-K 证据召回的最小数据流）**：
```python
# 1. 调用 /v1/embeddings 把用户问题和制度分块转成单位向量
# 2. 算夹角余弦并取前 K 名高于阈值（如 >= 0.75）的片段注入提示词：

```
- **④ 实现后的真实效果**：实现后效果：无论用户问『退钱』、『返还货款』还是『取消订单拿回本金』，哪怕字面上没有一个词跟标题重合，向量夹角都能稳稳命中同一条退款制度。

## 分步代码拆解：分步看懂代码：成对清理旧消息 + 按相似度挑文档

阅读 lab07_context_rag.py 中的两段实用代码，重点看清它们解决什么实际问题：

### 1 · 成对打包防切碎 — 把模型的调用申请（assistant.tool_calls）和紧随其后的工具结果（role='tool'）绑在一个小列表里同去同留。
```python
while i < len(messages):
    msg = messages[i]
    if msg.get("role") == "system" and not units:
        pinned_system.append(msg)                  # 头部 System 规则永远置顶保留
        i += 1
    elif msg.get("role") == "assistant" and msg.get("tool_calls"):
        group = [msg]                              # 发现带工具调用的 assistant 消息
        i += 1
        while i < len(messages) and messages[i].get("role") == "tool":
            group.append(messages[i])              # 把配对的所有 tool 消息绑进同一个 group！
            i += 1
        units.append(group)
    else:
        units.append([msg])
        i += 1
```
- **核心要点**：就这么一段简单的循环分组！分好组之后再删旧记录，就永远不会删出一半残留导致 API 报 400 错误了。

### 2 · 本地体验相似度打分 — 本地教学用标准库算两个数字列表的相似度（生产环境直接调向量数据库接口即可，不用背这段代码！）。
```python
def cosine_similarity(vec_a: list[float], vec_b: list[float]) -> float:
    # 工程提示：这个函数在真实项目里通常由 pgvector / Milvus / ES 内部实现，你只需会读它返回的 0~1 分数即可！
    norm_a = math.sqrt(sum(x * x for x in vec_a))
    norm_b = math.sqrt(sum(y * y for y in vec_b))
    dot_product = sum(x * y for x, y in zip(vec_a, vec_b))
    return dot_product / (norm_a * norm_b)
```
- **核心要点**：不用纠结里面的平方根计算——只要记住输出 0.99 代表两句话意思高度一致，输出 0.05 代表风马牛不相及就够了！
